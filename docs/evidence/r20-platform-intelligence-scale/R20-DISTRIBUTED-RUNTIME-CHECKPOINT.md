# R20 Distributed Runtime Checkpoint

Recorded: 2026-09-20
Branch: `forger-digital-solutions-forgegreen-certified`
Spend: `$0`
Environment: local WSL Ubuntu PostgreSQL 16, dedicated `codeforge_test_db`, test-only user `codeforge_test`; no production or Supabase access; all evidence generated by real subprocesses and independent PostgreSQL connections, never simulated within one pool

## Scope

This checkpoint advances the hosted runtime from "one durable authority with local workers" to "one distributed system across independent processes": cross-process cancellation signalling, durable fan-out budgets, post-dispatch outcome honesty, multi-instance capacity/fairness proofs, and a measured queue-head optimization. It does not certify any hosted topology, provider supply, or production surface.

## Migrations

- **013** (`hosted_execution_depth_and_dispatch_identity`): `depth` (computed at enqueue under the parent lock) and `provider_dispatch_id` (the provider-visible dedupe identity, only persisted for adapters declaring `supportsDispatchIdentity`).
- **014** (`hosted_executions_queued_route_user_head`): partial index `(provider_id, user_id, priority DESC, created_at) WHERE status='queued'`, added when the claim head was computed by `DISTINCT ON`.
- **015** (`hosted_executions_queued_user_route_head`): drops the 014 index and creates `(user_id, provider_id, priority DESC, created_at) WHERE status='queued'`. The claim query was rewritten to a recursive per-user skip-scan plus a per-user head probe; the 014 route-leading index could not satisfy that ordering and misled the planner into ~167-entry scans per probe.

## Cross-Process Cancellation

Mechanism: `pg_notify` inside the cancellation transaction (delivered post-commit) on channel `hosted_execution_events`, payload = correlation ids only (never prompts, payloads, credentials, or provider output). Payloads are bounded; a fan-out that exceeds the cap degrades to `"*"` — a resync marker — instead of silently truncating the id list. Receivers never trust the hint: `observeCancellations` re-reads durable rows and aborts only confirmed-terminal executions.

Delivery paths, both proven with real two-process evidence (`scripts/r20-postgres-remote-cancel.mjs` → `03-managed-free/results/postgres-remote-cancel.json`):

| Scenario | Mechanism | Commit→abort | Result |
|---|---|---:|---|
| `listen` | LISTEN/NOTIFY on dedicated listener connection | ~1–2 ms | aborted, durable `cancelled` |
| `poll` | worker's bounded durable poll (400 ms cadence), no subscription | ~375 ms | aborted, durable `cancelled` |
| `cascade` | parent cancel on controller connection → child abort on worker process | ~1 ms | aborted, both durable `cancelled` |

Listener lifecycle correctness: dedicated connection (never the shared pool), single-flight open (concurrent subscribe/reconnect cannot leak untracked LISTEN clients), bounded-backoff reconnect, resync event emitted on every reconnect, `close()` prevents a connect-in-flight from being installed after shutdown, SQLite parity via in-process emitter fired after commit.

## Multi-Instance Admission Proof

`scripts/r20-postgres-multi-instance.mjs` → `03-managed-free/results/postgres-multi-instance.json`.

**Phase A** — four real worker subprocesses raced 12 executions (4 users × 3) on one route at capacity 4, `maxUserConcurrent=1`:

- peak concurrent active leases: **4** (saturated, never exceeded), measured by committed `created_at`/`released_at` interval sweep — not polling, so no sampled peak can be missed
- claim-once: 12 claims, 12 distinct executions, `attempt=1` for all — `FOR UPDATE SKIP LOCKED` held under real cross-process contention
- fair first window: the first 4 claims covered 4 distinct users; every user received exactly 3 claims (no starvation)
- concurrent duplicate `idempotency_key` enqueue: exactly one row, both callers received the same execution

**Phase B** — server death: a worker SIGKILLed inside provider execution (post-`dispatched_at`) left its lease to expire; `recoverExpiredHostedLeases` moved the execution to `recovery_pending`, and fail-closed resolution terminalized it `failed` with the ambiguity recorded — no invented provider outcome.

## Fan-Out Budgets and Tree Integrity

- `HostedFanOutLimits` (`maxChildrenPerParent`, `maxDescendantsPerRoot`, `maxDepth`) enforced inside the enqueue transaction under row locks — never client-supplied.
- Ancestor-first locking (root → parent) matches the cancellation cascade's lock order: concurrent child-enqueue vs parent-cancel cannot deadlock, and a child cannot be admitted under a parent that is mid-cancellation ("late child revival" closed).
- Idempotency replay is evaluated before budget checks, so a retried enqueue does not consume budget.
- Forged `rootExecutionId` rejected; children of terminal parents rejected; cross-user parent access rejected; depth persisted and used for `maxDepth`.
- `getHostedExecutionTreeStats` returns owner-scoped aggregate counts (by status, active descendants, dispatch attempts, max depth) — no payload disclosure.

## Post-Dispatch Outcome Honesty

Dispatch outcome classes: `safe_retry` (provider dedupes the persisted dispatch identity), `safe_reconcile` (provider exposes lookup), `ambiguous` (outcome unknowable — fail closed), `not_dispatched` (pre-acceptance failure — ordinary retry safe).

- `ProviderAdapter.supportsDispatchIdentity` + `ChatRequest.dispatchId`: the runtime mints the execution's own id as the dedupe key only for adapters that transmit it; every other route stores `NULL` → ambiguous.
- `recovery_pending` requeue requires a persisted `provider_dispatch_id`; without it resolution fails closed — a worker dying after dispatch can never cause a blind retry that could double-execute.
- Stale-worker fencing is enforced at every mutation point: dispatch-mark, heartbeat renewal, and terminalization all verify the fencing `lease_token` (proven cross-connection and via the SIGKILL proof).

## Queue-Head Optimization (measured)

Evidence: `03-managed-free/results/postgres-admission-benchmark.json` (`scripts/r20-postgres-admission-benchmark.mjs`, fixtures 1k/10k/25k/50k queued, 200 users, EXPLAIN ANALYZE per size).

Original `DISTINCT ON` head selection scanned and sorted the provider's whole queued set — ~105–111 ms claim p50 at 50k queued with a ~700-block temp spill. The shipped rewrite has two layers:

1. **Recursive per-user skip-scan**: enumerates distinct queued users over `idx_hosted_executions_queued_user_head` — O(distinct queued users), not O(queued rows).
2. **Per-provider O(1) head probes**: `provider_id = ANY($3)` inside a probe defeats index ordering (ScalarArrayOp cannot preserve `(priority DESC, created_at)` order, so the planner scans every queued row the user has on the route and sorts). The probe instead `unnest`s the provider array and runs one equality-constrained probe per provider against `idx_hosted_executions_queued_user_route_head` — exactly the access shape that index serves. When no provider scope is given, a single probe against the user-head index keeps O(1). Per-user head semantics verified identical to the old formulation on live fixtures.

Final benchmark (`scripts/r20-postgres-admission-benchmark.mjs` → `03-managed-free/results/postgres-admission-benchmark.json`, 200 users, per-size route isolation, `VACUUM ANALYZE` before each measure to model steady-state autovacuum, `EXPLAIN (ANALYZE, BUFFERS)` per size):

| queued rows | claim p50 | claim p95 | claim max | head-query plan exec |
|---:|---:|---:|---:|---:|
| 1,000 | 53.6 ms* | 62.3 ms | 64.5 ms | 10.5 ms |
| 10,000 | 19.0 ms | 21.0 ms | 24.4 ms | 7.2 ms |
| 25,000 | 17.1 ms | 21.5 ms | 30.3 ms | 6.2 ms |
| 50,000 | 14.5 ms | 17.1 ms | 37.9 ms | 8.6 ms |

\* the 1k sample ran first on a cold plan cache; every other size is flat. Claim latency is now independent of queue depth (O(queued users)), versus ~105–111 ms at 50k before.

Two correctness fixes fell out of the measurement loop, both latent clock-domain bugs between the Windows test host and WSL PostgreSQL:

- `resolveHostedRecoveryPending` requeue reset `eligible_at = NOW()` (DB clock); a claim running milliseconds later with client `now` could not see the row while the DB clock ran ahead. Requeue now preserves the original `eligible_at` — already in the past for any row that was previously claimed.
- `hosted_capacity_leases.created_at` was client-stamped while `released_at` used `NOW()`; the multi-instance occupancy sweep mixed clock domains and reported a phantom `peakActiveLeases: 5` against capacity 4. `created_at` is now DB-stamped; the same sweep reports peak 4 = cap.

Remaining claim latency is transaction-statement overhead (advisory lock, capacity recheck, counts, update, lease insert, state upsert, receipt insert), not queue scanning; the serialized capacity critical section is intentional (it closed the earlier oversubscription P1) and was not weakened for speed.
